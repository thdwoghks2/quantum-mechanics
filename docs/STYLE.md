# 문체와 화면 가이드

모든 강과 사이트의 모든 글은 이 문서의 기준으로 쓰고 검사한다. 1순위는 **어떻게 하면 가장 잘 이해시키는가**다.
분위기(투박하고 살짝 어두운, 오펜하이머·인터스텔라 쪽)는 디자인이 맡고, 문장은 이해를 맡는다.
이 코스는 한 권의 책이고, 글쓴이 한 사람("저")이 독자와 같이 배우듯 이야기한다. 2장이 그 목소리다.

---

## 1. 하루 한 강

- 20분 안팎, **핵심 개념 하나**, 화면 18~25장
- 흐름: 장면 → 떠올리기 → 새 개념(정의·관찰·단계 설명) → 확인 → 숫자로 → 비유와 그 한계 → (이야기) → 되짚기 → 마지막 점검 → 한 문장으로 → 다음 강으로
- **되짚기**(`kind="recap"`, `<Recap terms>`): 오늘 나온 말(용어집에서 자동)과 오늘 온 길(번호 목록 3~5단계). 앞 단계가 뒤 단계의 이유가 되게 쓴다
- **마지막 점검**(`kind="problem"`, `<DailyProblem>`): 짧은 문제 하나. 단순 계산보다 오늘의 원리로 생각해야 풀리는 것. 힌트는 1~2개, 마지막에 풀이
- **한 문장으로**(`kind="one"`, `<OneLine>`): 오늘 배운 걸 독자가 한 문장으로 쓰고, 제 한 문장과 비교한다
- **다음 강으로**: 오늘 배운 것으로 설명되지 않는 사실 하나를 구체적으로 보여주고, 다음 강에서 무엇을 하는지 말한다. 수수께끼로 끝내지 않는다

## 2. 목소리

### 2-0. 누가, 어떻게 말하나

- **글쓴이 한 사람, "저/제가"**. 독자와 같이 배우는 사람이다. 독자와 함께일 때는 "우리", 권할 때는 "~해 보세요". "필자", "여러분", "학생들"은 쓰지 않는다
- **가르치는 목소리가 바탕**이다. 잘 아는 사람이 옆에서 차근차근 설명해 주는 말투로 쓴다. 가끔 말을 거는 한마디("이상하죠?")나 혼잣말("음, 여기서 하나 걸려요.")을 넣어도 되지만, 한 강에 두세 번만 양념처럼 쓴다. 반말, 호들갑, 감탄은 쓰지 않는다
- **해요체**. ~해요, ~이에요/예요, ~거든요(이유), ~잖아요(같이 아는 것), ~죠(확인)를 내용에 맞게 섞는다. 같은 끝맺음이 네 번 넘게 이어지지 않게(검사함)
- 합니다체와 "~다"체는 쓰지 않는다. 예외는 셋: 따옴표 안의 인용과 법칙 문장("물은 100 ℃에서 끓는다"), 그림 속 짧은 이름표("같은 일을 여러 번 보기"), 용어집 정의(명사로 끝나는 사전식 한 줄)
- **말하듯 자연스럽게**. 주어와 서술어를 갖춘 보통 어순으로 쓴다. 도치, 끊어치기("…없는데도요."처럼 이음말로 끝나는 조각 문장), 절을 명사구로 눌러 담기, 이상한 말로 길게 늘어놓기는 하지 않는다
- **쉬운 말**. 잘 안 쓰는 한자어, 고유명사, 전문어로 함축하지 않는다. 관측하다→보다, 상이하다→다르다, 해수면→바닷가 높이. 화면의 이름표도 쉬운 말로 쓴다(헷갈림 주의, 잠깐, 되짚기)

### 2-1. 같이 배우는 태도

- **인과를 한 걸음씩**. "왜 그럴까요?"는 바로 다음 문장이 답할 때만 쓴다. "그래서", "그러니까", "~거든요"로 이유와 결과를 잇는다
- **막히는 곳에서 멈춘다**. 아이들이 실제로 헷갈리는 대목에서 `<Note>`로 "저도 처음엔 여기서 멈췄어요" 하고, 다른 예로 한 번 더 푼다. 몰랐던 척 연기하지 않는다. 한 강에 한두 번
- **핵심 문장은 천천히 길게**. 조건과 이유를 다 담은 한 문장으로 쓰고 `<Key>`로 따로 세운다. 짧게 끊지 않지만 핵심은 살린다. 한 화면에 하나까지
- **진지할 곳에서는 진지하게**. 인물이 중요한 결정을 내리는 장면, 이 책의 큰 질문이 나오는 곳에서는 감탄과 농담 없이 차분히 쓴다
- **인물과 사건은 개념 안으로**. 그 사람이 무엇에 막혔고, 무엇을 했고, 그래서 무엇이 바뀌었는지가 오늘의 개념과 이어지게 쓴다. 기록된 사실만 쓴다
- **글쓴이의 경험은 짧게**. 개념을 돕는 것만 쓴다("일부러 버린다는 게 무슨 뜻인지, 저는 지하철 노선도를 보고 처음 제대로 이해했어요"). 확인할 수 있는 사실처럼 꾸미지 않는다

### 2-2. 한눈에 들어오는 화면

- 화면마다 덩어리 하나. 한 번에 보이는 글은 1~3문장이나 짧은 목록(2-3 속도와 밀도)
- 쓸 수 있는 장치를 섞어서 지루하지 않게 한다. 같은 모양의 화면이 세 장 넘게 이어지지 않게

| 장치 | 쓰는 곳 |
|---|---|
| **굵게** | 그 화면에서 꼭 가져갈 말 하나 |
| 번호 목록 | 순서, 단계, 인과의 사슬 |
| 점 목록 | 나란히 놓인 것들 |
| `<Key>` | 핵심 문장 하나 |
| `<Note>` | 글쓴이가 잠깐 멈춰 다시 짚는 말 |
| 표, 비교 패널, 큰 숫자 | 숫자와 두 경우의 차이 |

- 화면마다 목차에 보일 `title`을 붙인다. 10자 안팎의 이름("교통 법규와 자연의 법칙")

### 2-3. 속도와 밀도

휴대폰에서 글이 꽉 차 보이면 답답하고, 한 화면에 생각이 여러 개 들어 있으면 빠르게 지나간다고 느낀다.
그래서 **화면을 늘리고, 한 화면의 글은 줄인다.** `npm run lint:style`이 아래를 검사한다(해요체 강).

- 한 번에 보이는 글은 **3문장까지**. 더 말해야 하면 `<S n={2}>`로 다음 단계에 두어 "계속"을 눌러야 보이게 하거나, 화면을 쪼갠다
- 한 화면의 글은 단계까지 합쳐 **5문장까지**. 목록 줄과 `<Key>`, `<Note>`의 글은 따로 센다
- 한 문장은 60자 안팎, **75자(띄어쓰기 포함)를 넘지 않게**. `<Key>`만 예외로 길어도 된다
- **같은 끝맺음이 네 번 이어지지 않게**. "~어요"만 계속되면 단조롭다
- `<Key>`와 `<Note>`는 한 화면에 함께 두지 않는다. `<Note>`는 4문장까지이고, 필요하면 그 화면을 따로 만든다
- 한 강은 22~30장이어도 괜찮다. 장 수보다 한 장의 가벼움이 중요하다

## 3. 화면 설계

### 3-1. 화면 한 장

휴대폰 세로 화면(390×844) 한 장에 스크롤 없이 들어가는 것이 기준이다.

```
┌────────────────────────────────┐
│ 27강 · 열복사        ▮▮▮▮▯▯▯▯ 4/20 │  진행 표시
├────────────────────────────────┤
│        시각 자료 영역             │  화면 높이의 40~55%, 화면마다 하나
├────────────────────────────────┤
│ 글 2~4문장, 120~250자            │  첫 문장은 앞 화면과의 연결
├────────────────────────────────┤
│  ‹ 이전                 다음 ›   │
└────────────────────────────────┘
```

### 3-2. 화면 종류 (`<Screen kind="…">`)

| kind | 이름 | 시각 자료 | 글 |
|---|---|---|---|
| scene | 장면 | 일상 장면 (`Panels`, `Icon`) | 독자가 겪어 본 상황 |
| recall | 떠올리기 | 원래 강에서 쓴 그림을 그대로 | 그 내용을 실제로 다시 설명. `from={강}` |
| define | 정의 | `<Define term="…" />` | 왜 이 이름이 필요한지 |
| observe | 관찰 | 시뮬레이션 | 조작 지시 → 조작 뒤 해석(`<S n={2}>`) |
| graph | 그래프 읽기 | `Plot`에 `axisSteps`, 요소마다 `step` | 단계마다 한 문장 |
| step | 설명 | 이름표 붙은 도식 | 앞 화면에서 한 걸음만 |
| compare | 비교 | 두 경우를 나란히 | 무엇이 같고 다른지 |
| worked | 숫자로 | 표나 풀이 | 줄마다 왜 그렇게 하는지, 끝에 감각 확인 |
| analogy | 비유 | `<Analogy>` 대응표 | 맞는 곳과 틀리는 곳 |
| check | 확인 | (선택) | `<Check>`, `<Numeric>` |
| story | 이야기 | 연표, 인물 | 사람은 그 문제에 부딪힌 사람으로 |
| recap | 되짚기 | | `<Recap terms>`, 본문에 번호 목록 |
| problem | 마지막 점검 | | `<DailyProblem>` |
| one | 한 문장으로 | | `<OneLine>` |
| next | 다음 강으로 | | 구체적인 다음 질문 |

### 3-3. 시각 자료

- 화면당 하나, 메시지 하나, 이름표는 4개까지
- **물리량마다 고정 색**: 시간·주기·진동수(파랑), 거리·진폭·파장(초록), 속력·속도·가속도(보라), 힘·질량·운동량(분홍), 에너지(노랑), 전하(청록), 온도(주홍). 글에서 그 단어에도 같은 색 밑줄이 자동으로 붙는다
- 축 이름은 말로 쓴다: "진동수 (1초에 진동하는 횟수)". 단위 포함
- 빛을 다루는 그래프의 가로축은 사이트 전체에서 **진동수**이고, 오른쪽으로 갈수록 커진다
- 애니메이션은 개념이 움직임일 때만. 움직임을 줄이는 설정이면 자동 재생하지 않는다
- 모든 그림에 대체 텍스트(`alt`)

### 3-4. 글

- 한 번에 1~3문장, 화면 전체 5문장까지. 한 문장은 60자 안팎(2-3)
- 첫 문장은 왜 이 화면으로 넘어왔는지 말한다
- 숫자는 말로 먼저("1초에 약 400조 번"), 지수 표기는 2강에서 배운 뒤 함께
- 문장마다 주어와 서술어를 갖춘다. 절을 명사구로 눌러 담지 않는다
- 말투는 2장. 같이 배우는 사람의 해요체

## 4. 용어 계약

**한 번 말했다고 계속 쓸 수 있는 게 아니다.** 끌어다 쓸 수 있는 것은 자세하고 깊게 다룬 내용과 용어뿐이다.

1. 용어마다 **정식 도입 강**(`glossary.yaml`의 `taughtIn`)이 하나 있다. 정식 도입은 정의 카드, 일상 예시 2개, 시각 자료, 확인 문제를 모두 갖춘 것이다
2. 정식 도입 전에는 그 용어를 쓰지 않는다. 필요하면 풀어서 쓴다. 일부러 미리 언급할 때만 `<Later n={강}>…</Later>`로 감싼다. 앞 강들이 이미 일상어로 쓰던 말(원자, 분자, 전자처럼)은 그 용어의 용어집 항목에 `previewIn: [강 번호들]`을 적어 그 강들에서만 허용한다. 온도, 평균처럼 아주 흔한 일상어는 용어로 올리지 않고, 더 정확한 말(절대온도, 기댓값)을 용어로 둔다
3. 정식 도입 뒤에도 다른 강에서 처음 쓸 때는 괄호 풀이나 떠올리기 화면을 붙인다. 진동수(1초에 진동하는 횟수)처럼
4. **지어낸 말 금지**: 정식 용어가 아닌 줄임말("몫", "떨림")을 만들어 쓰지 않는다
5. **한 물리량에 한 이름**: "진동수"와 "주파수"를 섞지 않는다. 빛은 진동수로 설명하고, 파장이 필요하면 변환 문장을 따로 둔다
6. **비교하는 말에는 대상을 붙인다**: "짧은 쪽" 대신 "진동수가 높은 빛"
7. **그래프 말은 그래프와 함께만**: "꼭대기", "오른쪽"은 그래프가 화면에 있고 축을 말로 읽어 준 뒤에만

`npm run validate`가 1, 2를 강제한다.

### 4-1. 기호 계약

용어와 같은 규칙을 기호(알파벳·그리스 문자)에도 적용한다.

1. 기호마다 처음 배우는 강이 하나 있다(`symbols.yaml`의 `taughtIn`). 그 강에서 이름, 읽는 법, 뜻, 단위를 공식 카드나 기호 표로 보여 준다
2. 글자 모양으로 종류를 나눈다. 변하는 양은 기울인 글자에 그 물리량 색, 상수는 금빛에 아래 점선, 단위는 똑바로 선 회색, 번호는 옅은 네모 바탕
3. **한 강에 한 글자 한 뜻.** 높이 h와 플랑크 상수 h를 한 강에서 함께 쓰지 않는다. 피할 수 없으면 아래 첨자로 나눈다($m_e$, $k_B$)
4. 앞에서 같은 글자를 다른 뜻으로 배웠다면, 새 뜻을 처음 쓰는 화면에 `<Note>`로 "헷갈리지 마세요"를 단다. 기호 카드는 같은 모양의 다른 기호를 저절로 보여 준다
5. 기호가 셋 넘게 새로 나오는 식은 `<FormulaBuild>`로 한 덩어리씩 쌓는다. 한 화면에 새 기호는 둘까지
6. 식을 보여 준 뒤에는 말로 한 번 읽어 준다("힘 = 질량 × 가속도"). 기호만 늘어놓고 넘어가지 않는다

### 4-2. 공식 카드와 개념 카드

- 공식을 처음 배우는 강에는 공식 카드(`<Formula>`)를 둔다. 카드는 용어집의 '공식' 칸에도 모인다
- 강의 핵심 개념(`mechanism`)에는 개념 카드(`<Concept>`)를 둔다. "차근차근"에는 어려운 개념을 2~5단계로 나눈 순서를, "흔한 오해"에는 학생이 실제로 하는 오해를 적는다
- 말로만 설명한 관계("~할수록 ~해진다", "비례한다")는 그래프(`Plot`, 시뮬레이션)나 숫자 표로도 보여 준다

## 5. 설명 원칙

- 한 강에 핵심 개념 하나, 한 화면에 새 생각 하나
- 예시는 일상에서, 개념마다 서로 다른 장면 두 개 이상
- 비유는 구조가 같아야 한다. 비유 안에서도 같은 이유로 같은 결과가 나와야 하고, 틀리는 곳을 밝힌다
- 수식은 말 → 그림 → 숫자 → 기호. 기호는 처음 쓸 때 뜻과 단위를 적는다
- 흔한 오해를 먼저 꺼낸다
- 역사는 개념이 선 다음에. 설명 순서와 실제 역사 순서가 다르면 그렇다고 밝힌다
- `mechanism`(이 강이 설명할 원리 한 문장)을 먼저 적고, 본문이 단계별로 설명했는지 확인한다
- 독자가 실제로 해 볼 수 있는 것을 넣는다
- 기록으로 확인된 사실만 쓴다. 출처는 `sources`에

### 화면마다 묻는 점검 질문

- 이 화면에 정식 도입 전인 용어가 있나?
- 이 화면만 읽은 중학생이 모르는 단어가 있나? 무엇과 무엇을 비교하는지 빠진 말이 있나?
- 앞 화면에서 이 화면으로 넘어오는 이유가 글에 쓰여 있나?
- 방향어(쪽, 위, 꼭대기)를 그래프 없이 썼나?
- "그래서 그게 왜?"라는 반응이 나올 곳이 있나?

## 6. 무엇이 AI 말투이고 어떻게 고치는가

계획 단계에서 쓴 예시 글들을 진단한 결과다. `npm run lint:style`이 일부를 자동으로 찾는다(금지 표현, 명사형 종결, 글자 수, 방향어, 해요체 강에 섞인 "~다").

| # | 문제 | 예 | 왜 AI처럼 읽히나 | 고치는 법 |
|---|---|---|---|---|
| ① | 맥락 없는 고유명사 | "실험물리학자 하인리히 루벤스가 … 막스 플랑크의 집에" | 글쓴이가 아는 걸 독자도 안다고 가정 | 문단당 새 이름 하나, 누구이고 왜 나오는지 문장으로 |
| ② | 수수께끼 결말 | "문제는 그 식이 왜 맞는지였다" | 긴장감 흉내. 질문만 던지고 넘어감 | 무엇을 몰랐고, 무엇을 받아들여야 했고, 무엇이 바뀌었는지 |
| ③ | 날짜로 여는 명사형 문장 | "1900년 10월 7일, 일요일 오후." | 영화 오프닝 템플릿 | 날짜·장소는 타이틀 카드가 맡는다 |
| ④ | 끊어치기·도치 | "…맞지 않는다고." | 번역 소설의 리듬 | 완결된 문장, 인과는 접속어로 |
| ⑤ | 같은 길이 짧은 문장 연속 | | 연결어가 잘려 나감 | 문장 길이는 내용이 정한다 |
| ⑥ | 반전 공식 | "A였다. 문제는 B였다." | 어디에나 끼우는 틀 | 대비가 핵심일 때만, 양쪽을 구체적으로 |
| ⑦ | 지어낸 장면 | "플랑크는 책상에 앉았다" | 그럴듯한 질감을 위해 사실을 꾸밈 | 기록된 것만 |
| ⑧ | 일을 안 하는 디테일 | "아내와 함께", "차를 마시다가" | 분위기용 정보 | 빼서 잃는 게 없으면 뺀다 |
| ⑨ | 이유 없는 중요성 | | 전제하거나 선언만 함 | 무엇이 달라지는지 결과로 |
| ⑩ | 번역투 | "실험물리학자 하인리히 루벤스가", "그는" | 영어 구문 직역 | 역할은 문장 안에, 사람은 이름으로 |
| ⑪ | 독자 위치를 무시한 밀도 | "긴 파장", "기존 공식", "측정값" | 글쓴이 기준으로 씀 | `assumes`·`introduces` |
| ⑫ | 빠른 전개 | 다섯 문단에 개념 열두 개 | 빠짐없이 담으려는 요약 습관 | 한 강 한 개념, 한 화면 한 생각 |
| ⑬ | 설명 대신 경위 | 누가 무엇을 했는지만, 왜 맞는지는 없음 | 역사는 쉽고 원리는 어려워서 건너뜀 | `mechanism`을 먼저 적고 확인 |
| ⑭ | 구조가 다른 비유 | "1원 단위로 못 내고 동전으로만" | 모양만 닮고 원리는 안 닮음 | 비유 안에서도 같은 이유로 같은 결과 |
| ⑮ | 지어낸 말을 용어처럼 | "몫", "떨림의 종류" | 글쓴이는 뜻을 아니까 명확하다고 착각 | 진짜 용어를 정식 도입 강에서 가르친다 |
| ⑯ | 눌러 담은 명사구 | "가장 세게 내는 파장" | 절 하나를 명사구로 압축 | 주어와 서술어가 있는 문장으로 |
| ⑰ | 그래프 없는 방향어 | "짧은 쪽으로 옮겨 간다", "언덕" | 글쓴이 머릿속 그래프를 독자도 본다고 가정 | 용어 계약 7번 |
| ⑱ | 한 번 언급 = 배운 것 | "24강의 규칙에 따르면" | 강 번호를 대면 설명한 것으로 착각 | 떠올리기 화면에서 실제로 다시 설명 |
| ⑲ | 같은 것을 두 이름으로 | "파장이 짧은"과 "진동수가 높은"이 섞임 | 바꿔 쓰면 덜 반복적이라는 습관 | 한 물리량에 한 이름 |

그 밖에 금지: "필자", 질문으로 시작하는 도입, 답 없이 던지는 질문, 질문 연발, 개념의 의인화("자연은 허락하지 않았다"), 장식 은유("실재의 커튼"), 무엇이든 셋으로 묶기, 문단 끝 한 줄 여운, "여러분", "~에 대해 알아보겠습니다", "핵심은", "정리하자면", "흥미롭게도", "놀랍게도", 쌍점·줄표로 극적 효과 내기, 느낌표.
